# 模型：描述结构、字段语义与校验

> README 规定项目目标与规则；本文件规定描述结构、字段语义与校验。
> 写作规范、流程与项目约定见 [CONVENTIONS.md](CONVENTIONS.md)。

## 一、描述结构

```
Description = { items, routes, ambient? }

Item        = { id, name, category, unit, mass?, props?, holds?, consumption?, composedOf?,
                interface?, extends?, monolithic?, deferred? }
Component   = { item, select?, qty, wear?, need?, onRelax? }
Consumption = { item, qty, per }

Route       = { id, name, produces, uses, needs, performedBy?, under?, steps?, rate?,
                unbalanced_zh? }
Clause      = { anyOf: Option[] }
Option      = { item, qty, need?, onRelax? }
Step        = { note_zh?, performedBy?, under? }
Condition   = { param, min, max, record?, design? }
Qty         = { num, den }
```

### 字段总表

| 所属 | 字段 | 类型 | 含义 |
|---|---|---|---|
| Description | `items` | `Item[]` | 条目表 |
| Description | `routes` | `Route[]` | 路线表 |
| Description | `ambient` | `Condition[]` | 现场环境条件；落在区间内时不需要设备维持 |
| Item | `id` | `string` | 唯一标识 |
| Item | `name` | `string` | 中文名；只给人看，不参与判定；允许重名 |
| Item | `category` | `ItemCategory` | `material` / `part` / `consumable` / `carrier` / `machine`；缺省为 `material` |
| Item | `unit` | `string` | 计量单位：件、台、套等 |
| Item | `mass` | `Qty` | 单件质量，单位 kg |
| Item | `props` | `PropDecl[]` | 属性类型声明（range / enum / set） |
| Item | `holds` | `Condition[]` | 设备能维持的条件区间；仅 `machine` 可填 |
| Item | `consumption` | `Consumption[]` | 每运行小时的消耗件 |
| Item | `composedOf` | `Component[]` | 可逆组成清单：零件或子机器；不含材料 |
| Item | `interface` | `true` | 抽象接口；id 必须以 `iface/` 开头，只能有 `props` |
| Item | `extends` | `string` | 单继承一个 `iface/` 接口；不支持多级继承 |
| Item | `monolithic` | `boolean` | 无装配 BOM 的单件；`machine` / `part` 可用，须有理由注释，不能与 `composedOf` 同用 |
| Item | `deferred` | `boolean` | 明确尚未分解；仅 `part` / `consumable` 可用 |
| Component | `item` | `string` | 组成件 id：零件、子机器或 `iface/` 接口 |
| Component | `select` | `string` | `item` 为抽象接口时，指定具体实现 |
| Component | `qty` | `Qty` | 装几个 |
| Component | `wear` | `Wear` | 运行时磨损 |
| Component | `need` | `PropReq[]` | 装配这一步要求的规格窗口 |
| Component | `onRelax` | `'functional-kept' / 'functional-lost'` | `need` 达不到时的后果；写了 `need` 必须表态 |
| Consumption | `item` | `string` | 消耗件 id |
| Consumption | `qty` | `Qty` | 每 `per` 小时用掉多少 |
| Consumption | `per` | `Qty` | 运行小时 |
| Route | `id` | `string` | 唯一标识 |
| Route | `name` | `string` | 中文名；只给人看，不参与判定；允许重名 |
| Route | `produces` | `Term[]` | 产出项；`produces[0].qty` 定义一批的产量 |
| Route | `uses` | `Clause[]` | 一批的消耗；若干子句为 AND，每个子句内为 OR |
| Route | `needs` | `Need[]` | 必须存在但不被消耗的前提 |
| Route | `performedBy` | `string` | 单工序路线的执行设备；必须是 `machine` |
| Route | `under` | `Condition[]` | 单工序路线进行期间必须维持的条件 |
| Route | `steps` | `Step[]` | 多工序链；与路线级 `performedBy` / `under` 互斥 |
| Route | `rate` | `{ hours: Qty }` | 一批占用的小时数；不含排队 |
| Route | `unbalanced_zh` | `string` | 声明质量不平衡并说明原因 |
| Term | `item` | `string` | 产出条目 id |
| Term | `qty` | `Qty` | 产出数量（配比） |
| Term | `gives` | `PropReq[]` | 这条路线交付的规格窗口 |
| Clause | `anyOf` | `Option[]` | 任选其一的输入选项 |
| Option | `item` | `string` | 选项条目 id |
| Option | `qty` | `Qty` | 该选项的数量 |
| Option | `need` | `PropReq[]` | 该选项要求的规格窗口 |
| Option | `onRelax` | `'functional-kept' / 'functional-lost'` | 放宽窗口后的后果 |
| Step | `note_zh` | `string` | 工序名称；只给人看 |
| Step | `performedBy` | `string` | 该段的执行设备 |
| Step | `under` | `Condition[]` | 该段必须维持的条件 |
| Condition | `param` | `string` | 参数名：温度、压力、气氛等 |
| Condition | `min` / `max` | `number` | 条件区间的下界 / 上界 |
| Provenance | `record` | `string` | 读数出处：`measure/*` 产出的记录条目；`Condition` / `PropReq` 继承此字段 |
| Provenance | `design` | `true` | 明标设计窗口；不算实测，审计不算满足 |
| Qty | `num` / `den` | `number` | 正有理数的分子 / 分母 |
| Wear | `amount` | `Qty` | 每 `per` 小时损耗的比例，(0, 1] |
| Wear | `per` | `Qty` | 运行小时门槛 |

`Need` 为 `string | Option`：字符串表示“至少在场一件”，`Option` 可再带数量与规格窗口。
`Option.qty` 在 `uses` 中表示消耗量，在 `needs` 中表示在场数量下限。

`name` 是展示名，`id` 是身份：改名不影响引用，id 不得随改名而变。
`validate` 只拒绝空名，不要求重名唯一。

`PropDecl` 的 `range` 使用 `min` / `max` / `unit` / `dir`，`enum` / `set` 使用 `values`。
`PropReq` 的对应窗口使用 `min` / `max` / `dir`、`oneOf`、`atLeast`，并可带 `record` / `design`。

## 二、定义与制造分离

| 类别 | 回答 | 载体 |
|---|---|---|
| **定义** | 对象是什么 | `Item`：类别、单位、质量、组成件、可维持条件 |
| **制造** | 对象如何产生 | `Route`：材料、设备、条件、联产 |

定义与制造的分界判据为：该事实能否由条目自身回答。

```
床身重 820 kg，由 HT300 铸铁构成     → 定义（Item.mass）
用铁水浇成                            → 制造（Route.uses）
```

二者混合将导致工艺变更引起定义变更。分离后，工艺变更仅修改路线，条目保持不变。

条目不得写入材料；材料只出现在 `Route.uses`。在条目上写 `material: '40Cr'`
等同于重复路线中已有的投料，且重复内容难以校验。

已知例外为 `Item.consumption`：该字段描述机器每运行小时消耗的消耗件，属于制造一侧；
但其计量单位为运行小时，而路线按批次计量，刻度不同，故暂留于条目。

## 三、装配与加工

`items` 与 `routes` 分离的根本依据是两种关系，而非名词与动词之别：

| 关系 | 载体 | 可逆性 | 拆分后的状态 |
|---|---|---|---|
| **空间组合** | `Item.composedOf` | 可逆 | 每个零件仍为零件，可装至其他位置 |
| **加工** | `Route` | 不可逆 | 材料改变形状，无法恢复 |

```ts
// 装配体：十一个零件，拆开后均可继续使用
{ id: 'plant/milling-machine', composedOf: [{ item: 'plant/milling-machine/bed', qty: q(1) }, ...] }

// 加工件：铁水浇成床身，不可逆
{ id: 'make/mill-bed',
  produces: [{ item: 'plant/milling-machine/bed', qty: q(1) }],
  uses: [{ anyOf: [{ item: 'mat/iron-ht300', qty: q(1) }] }] }
```

二者可并存：`composedOf` 表示“由哪些零件组成”，产出路线表示“如何制造”。
装配路线写工艺（`performedBy` / `steps` / `under`）；零件不写入 `uses`，
`uses` 只记录不可逆加工的消耗。

无产出路线的条目构成缺口：`composedOf` 只回答“是什么”，不回答“如何产生”。
`--tasks` 中“建装配路线”统计的即为这些条目。

## 四、数量与质量

```ts
{ id: 'plant/milling-machine/bed', unit: '件', mass: q(820), category: 'part' }
{ item: 'plant/milling-machine/bed', qty: q(1) }     // 装 1 个，不是 820 kg
```

- `qty` 表示装配数量，单位为件。
- `mass` 表示单件质量，单位为 kg。

一台铣床为 **1 台**，质量 2568 kg，不得表述为“2568 kg 铣床”。
将 `unit` 写为 `'kg'` 会使 BOM 读作“装 820 kg 床身”；BOM 的正确含义是
“装 1 个床身，其质量为 820 kg”。

计量单位只有三个刻度：时间按运行小时，质量按 kg，数量按件或台；模型不提供换算表。

零件声明 `mass` 时，其产出路线投入的材料总质量必须相等，否则触发 `mass_mismatch`。
未声明 `mass` 的零件（铸件质量随工艺与余量变化）不受此约束。

## 五、标识规则

零件标识采用路径形式，不使用扁平名。`machine_base` 无法表明所属机器；
两台机器各有一个床身时无法区分。路径携带归属，并可被程序处理：

```ts
leaf('plant/milling-machine/tool-changer')   // 'tool-changer'   零件名
owner('plant/milling-machine/tool-changer')  // 'plant/milling-machine'  所属机器
```

校验强制零件路径以所属机器 id 为前缀，否则触发 `bad_component`。

id 仅表示对象身份，不表示来源。种子是清单，不是前缀；`seed/robot` 属于错误写法。
判据为：该事实能否在其他位置修改；若能，则不得写入名称。

零件 id 有两种形态：

```
<machine>/<name>   专用件，规格由机器决定
std/<type>-<spec>  标准件，规格独立于使用者
```

判据为规格由谁决定。`std_without_spec` 拦截无规格标准件；`std_single_use` 仅提示。
“只被一台设备使用”属于用量症状，不是判据。现有 8 条不改；出现第二台且规格要求不同时再拆分。

## 六、消耗件与磨损

| 类别 | 安装位置 | 用尽后的处理 | 载体 |
|---|---|---|---|
| **零件** | 安装在机器上 | 磨损后更换，机器恢复 | `Component.wear` |
| **消耗件** | 不安装在机器上 | 被消耗，无法恢复 | `Item.consumption` |

```ts
// 零件：磨损记录挂在会磨损的零件上，不写在整机上
{ item: 'plant/milling-machine/way', qty: q(1),
  wear: { amount: q(1), per: q(40000) } }     // 四万运行小时报废

// 消耗件：不进入零件清单，按运行小时消耗
consumption: [{ item: 'consumable/insert', qty: q(1), per: q(20) }]
```

磨损记录应挂载于实际磨损件。床身不磨损，磨损的是其上的导轨；更换对象为导轨而非床身，
此即路径标识相对于扁平名的用途。

磨损必须绑定运行时长。`wear: q(1, 12000)` 挂载于整机时无法说明 12000 的计量对象：
批次数不是时间；路线才有批次，零件没有批次。

模型只使用一个时间刻度：运行小时。日、月、年虽可换算，模型不提供换算。
设置多个可换算单位而不提供换算，会使 `40000 小时` 与 `5 年` 成为不可比较的数值。

## 七、工序表达

模型不设独立工序字段。工序若仅以自由文本记录，既不能比较，也不能执行。
`Component` 只表达组成件、数量、装配要求与磨损，不表达工序。
材料牌号是可核对的字符串，工序不是。工序写入 `Route`。

`performedBy` 只有一个位置，因此仅用于**单工序**路线。接力工序（车、滚齿、调质、磨）
使用 `steps` 表示：每段一台设备、一组条件，物料流仍写在路线级。
路线级 `performedBy` / `under` 与 `steps` 不得同时出现；同时写入触发 `step_conflict`。
每段执行者必须是设备（`not_a_machine`），且不得同时裸写在 `needs` 中（`redundant_need`）。
材料只写在路线级。

```ts
steps: [
  { note_zh: '车', performedBy: 'lathe' },
  { note_zh: '调质', performedBy: 'plant/reduction-furnace', under: [...] },
  { note_zh: '磨', performedBy: 'plant/grinder' },
]
```

无执行者的情形分为三类：

```
① 自然完成（晒盐、自烧结、随炉固化）
② 前提是设备（窑内焙烧，窑写在 needs）
③ 缺设备（压机、拉丝模）：属于缺口，不是豁免
```

装配、砌筑、配液等需要人工操作的工序，执行者填写 `plant/robot`。

## 八、校验

`validate(d)` 只检查描述是否写对，不进行求解。与条目直接相关的错误码如下：

| 错误码 | 拦截内容 |
|---|---|
| `bad_component` | 零件清单错误：非零件、重复、路径不以所属机器开头 |
| `unknown_item` | 引用未声明条目 |
| `bad_quantity` | 数量不是正有理数 |
| `mass_mismatch` | 声明 `mass` 的零件与路线投料不守恒 |
| `part_as_raw_material` | 零件被当作原料投入路线；该零件应进入 `needs` |

同一判据对同一对象只报告一次：路线级检查置于路线循环，条目级检查置于条目循环。
反例测试应保证“错误数不随条目数变化”。

其余错误码与提示的完整清单见 `pnpm check` 输出。

## 九、链完整性检查

一条链写完整须通过四项检查：

```
料    Route.uses      每个投料均有产出者，直至落到火星表面物质（R6）
条件  Route.under     每个 param 均有设备在 holds 中维持
设备  performedBy     每台设备均可达（种子除外），且不被自身产品路线的 needs 引用
联产  produces        副产物均有去处；否则缺口被转移而非消除
```

四项全部通过，链才算写完整。缺失环节及其量级按 R7 记录，不得写“不可行”（R4）。

## 十、降级

```
可降级：精度、效率、寿命、自动化、通量、材料牌号
不可降级：感知、决策、力控，以及任何需要“判断”的动作
```

判据为：替换后是否仍能完成原功能。

- `onRelax: 'functional-kept'`：以较低规格承担同一功能，属于降级，须提供升级路线；
- `onRelax: 'functional-lost'`：替换为另一对象，不属于降级，属于另一问题（R3）。

机器人为唯一不可降级项；种子自给表使用 `NOT_BUILDABLE` 显式名单。

## 十一、node 与 lineWidth

`node` 表示该工艺世代的名义栅长（nm），容差 ±25%。互连线宽是独立判据 `lineWidth`，
不参与 `node` 计算。40 nm 档判据为 ≤50，8 nm 档判据为 ≤10。

## 十二、设计窗口与出处

窗口只有两种出处：`record` 与 `design`；两者均不写时为 `bare`（历史口径）。

- `record` 指向 `measure/*` 产出的记录条目。记录中的窗口是读数，路线 `gives` 是量程。
- `design: true` 明标设计窗口：该区间由设计给出，本层没有读数。审计不将其视为满足；
  交付窗口、`holds`、`under` 均不构成满足。

移除 `design` 的唯一依据是测量：`measure/*` 路线收窄窗口并产出记录。
设备 `holds` 覆盖同一区间不构成测量；`holds` 是能力声明，不是读数。
它可使非 `design` 条件成立，但不能使 `design` 窗口成为已测。

审计校验 `record` 的出处：记录条目必须存在、由 `measure/*` 产出、当前可达，且记录窗口落在引用窗口内；不合规的 `give` 不算交付。
删除 `design` 后，窗口回落到 `bare`，仍按历史口径放行；因此“去 design”不能只靠删字段，须依靠数据纪律：

1. 先补测量路线与记录，再删除 `design`；
2. 记录须给出窗口内的实测区间与不确定度，不得原样复述设计窗口；
3. 删除 `design` 的差异须指向对应的 `measure/*` 与记录条目。

示例：条件写 20–30 °C 属于设计窗口；记录读出 23–27 °C 才构成收窄。
以“设备 holds 20–30”为由删除 `design`，是将能力声明当作读数。

## 十三、描述真实性要求

模型允许省略，但不允许以省略掩盖缺口。字段级要求如下：

1. **条目可追溯**：条目应具有可追溯的设计依据、产出路线或来源；未分解者标 `deferred`，不得虚构生产者。
2. **路线符合工艺**：`uses` 为实际消耗，`composedOf` 为实际组成件；种类、数量与来源应一致，无来源者标为假设。
3. **粒度一致**：存在组成件时应使用 `composedOf`，未分解时使用 `deferred`；`monolithic` 仅限无独立组成件的单件。
4. **审计必要但不充分**：审计不证明 BOM、工艺或数量；失败应补充描述或记录缺口，不得修改标识、合并条目或虚构输入。
5. **闭合判定**：审计通过、L0–L3 证据支持、关键条目可追溯，三者同时满足。

审计将 `deferred` 条目单列报告；其产出路线按 `DEFERRED_PRODUCT` 阻断，不得视为可制造。

应避免：

| 做法 | 后果 |
|---|---|
| 为达到可达性而修改标识、合并条目 | 以审计结果替代事实判断 |
| 对含多个组成件的装配使用 `monolithic` | 以标记掩盖未分解结构 |
| 在 `composedOf` 中填写未经证实的零件或数量 | 审计通过而 BOM 失真 |
| 将 `deferred` 作为长期省略手段 | 缺口未被记录，无法继续推导 |
| 仅报告审计通过，不报告 L1–L3 证据 | 将必要条件误作充分条件 |
